1. Source-of-Truth and Revision Decisions
ADM-F001 FSD v1.0 remains the source for registration validation, identity uniqueness, authentication, Applicant ID / Application ID / reference generation and registration notifications.
The latest implementation decision changes the physical model from separate Applicant Account + Application entities to one application record. Registration identity and later application profile data are stored in the same row.
ADM-F001 is intentionally limited to the registration/authentication flow. Programme selection, academic information, profile completion, declaration and submission belong to ADM-F002.
ADM-F002 must update the existing ADM-F001 application record rather than creating a second personal/applicant record.
The same business attribute must have one authoritative storage location. No duplicate applicant_name, email, CNIC/passport or mobile columns may be introduced in ADM-F002 tables.

4.2 Constraints and No-Duplication Rules
UNIQUE (intake_session_id, normalized_registered_email).
UNIQUE (intake_session_id, normalized_cnic_passport_number).
application_id is a generated business identifier, globally unique and never reused; applicant_id is the stable internal primary key.
application_reference is unique.
ADM-F002 must reference admissions_applications.applicant_id and must not create another applicant/personal-information master.
Registered email is displayed read-only and is not copied into any F002 child table.
Applicant name, identity document number and mobile number have one authoritative copy in admissions_applications.
Country/province/city are reference masters; application-specific addresses belong in the F002 application-address table, not in admissions_applications.

8. Registration Notification and Audit
Registration confirmation contains Applicant ID, Application ID and application reference.
WhatsApp is the primary channel; email and SMS are also dispatched according to the FSD.
Notification failure must not create a second application record or roll back a successful registration unless a future business decision explicitly requires synchronous notification.
Store channel, dispatch timestamp, delivery status and acting system identity for audit.
9. Security and Authorization
Password is stored only as a secure hash.
Identity and credential fields are sensitive and must not be logged in plaintext.
Applicant requests are scoped to the authenticated applicant_id.
Cross-tenant or cross-application access is rejected without disclosure.
Registered email remains immutable through applicant application APIs.
