1. Revised Implementation Decisions
ADM-F002 uses the existing application row created by ADM-F001; it does not create a second applicant/personal-information record.
The four-step applicant flow is implemented in this order: Academic Information → Programme Selection → Profile → Declaration.
The latest project-defined order supersedes the sequence shown in the current ADM-F002 FSD for implementation. The FSD business rules remain applicable unless they conflict with this explicit sequencing decision.
Academic Information is a repeating child collection. Each academic record has a degree type such as Matric, FSC, etc.
Academic supporting documents are stored in a separate child table linked to the relevant academic information record.
Application addresses are normalized into a separate application-address table and reference the existing Country, Province and City masters.
Application contacts are normalized into a separate application-contact table with a contact_type such as PARENT or GUARDIAN. Emergency contact remains distinguishable by contact type/role and must satisfy the blood-relation rule.
Applicant identity fields already stored in admissions_applications are updated there by the Profile step; they are not copied into F002 child tables.

Implementation can use 0/25/50/75/100% for four completed steps, unless the project defines a different completion formula.

13. Data Integrity Constraints
All F002 child tables use applicant_id as the parent foreign key.
No F002 table duplicates registered_email, password_hash, application_reference or cnic_passport_number.
No F002 table duplicates applicant name/mobile as an applicant master; Profile updates the shared admissions_applications row.
Academic information is one-to-many per application.
Academic documents are one-to-many per academic information record.
Programme selection is one-to-one per application, with one-to-two programme option rows.
Addresses are one-to-many by address_type with uniqueness enforced for PRIMARY and SECONDARY where applicable.
Contacts are one-to-many by contact_type; contact_type controls parent/guardian/emergency semantics.
Declaration is one-to-one per application.
14. Security, Audit and Storage
Profile photographs and academic documents are stored through the approved document storage service; the database stores file references and metadata.
CNIC/passport and disciplinary information are sensitive and must not be exposed in logs or broad reporting APIs.
All child-record access must verify the authenticated applicant owns the applicant_id.
Profile and child data remain editable until approval; after approval, applicant APIs become read-only.
Audit step saves, submission, declaration acceptance, document uploads and profile changes.

16. Acceptance Criteria — Revised
Applicant begins F002 using the application record created by F001.
Academic Information is the first step and requires at least one complete academic record.
Each academic record supports a degree type such as Matric or FSC and can have supporting documents.
Programme Selection is the second step and permits a maximum of two published programme preferences.
Profile is the third step and updates the shared admissions_applications row without duplicating identity data.
Addresses reference existing Country, Province and City tables through foreign keys.
Contacts use contact_type to distinguish Parent, Guardian and Emergency contacts.
Declaration is accessible only after Academic, Programme and Profile steps are saved.
Submission requires declaration acceptance, disciplinary response/details and valid test-centre selection.
Successful submission sets the application to Complete (Submitted), 100% completion and records the submission timestamp.
Notification failure does not roll back a committed submission.
Approval makes the applicant's application read-only.

Declaration Configuration — Admin Controlled
ADM-F002 shall include the declaration configuration required for the applicant Declaration step. The declaration is created/configured by an authorized admissions administrator before applicants can complete Step 4. The applicant only reads the active declaration and records acceptance; the applicant does not create or edit the declaration text.

Declaration API Ownership
These endpoints are F002-owned because the declaration is part of the F002 submission contract. They serve both the administrative configuration side and applicant consumption side; existing IAM authorization is reused.
Admin API
POST /api/v1/admin/applications/declarations — create a declaration for an intake.
Admin Update API
PUT /api/v1/admin/applications/declarations/{declaration_id} — update a declaration while it is DRAFT.
Admin Activate API
POST /api/v1/admin/applications/declarations/{declaration_id}/activate — activate the declaration for its applicable intake.
Admin Read API
GET /api/v1/admin/applications/declarations?intake_session_id={intake_session_id} — list declarations for an intake.
Applicant Read API
GET /api/v1/applicant/applications/{applicant_id}/declaration — return the active declaration applicable to the applicant's intake and the applicant's current acceptance state.
Applicant Acceptance
PUT /api/v1/applicant/applications/{applicant_id}/declaration — record acceptance against the currently active declaration version. The declaration text itself is not editable by the applicant.

Declaration Rules
├── Declaration must exist before Step 4 can be completed.
├── Applicant sees the active declaration associated with the application's intake.
├── Applicant cannot modify declaration text or version.
├── Acceptance records the exact declaration version presented.
├── A submitted application retains the accepted declaration version as an immutable submission record.
├── A new declaration version does not change historical applicant acceptance records.
└── If no active declaration exists, submission is blocked and the administrator must configure/activate one.

No Duplication / Boundary
ADM-F002 owns the declaration configuration and applicant acceptance contract. ADM-F001 remains registration-only and does not store or manage declaration text. The declaration is not duplicated into admissions_applications; the application declaration record stores the accepted declaration version/reference and acceptance details.
Programme Eligibility Validation After Academic Information
Source-backed boundary. ADM-F002 requires programme options to be validated against the published offering. ADM-F000 publishes admission criteria but explicitly does not evaluate applicant eligibility. Therefore automatic eligibility evaluation requires an approved eligibility-rule contract and must not be invented from the current FSD.
Recommended Applicant Flow
ADM-F002
└── 1. Academic Information
    ├── Applicant enters one or more academic records
    ├── Degree type (for example Matric, FSC, Bachelor, etc.)
    ├── Board / institution, passing year and marks / GPA
    └── Save academic information
└── 2. Programme Selection
    ├── Load programmes from the current published intake
    ├── Applicant selects Programme Option 1
    ├── Validate programme availability
    ├── Validate eligibility against saved academic information
    │   ├── Eligible → allow selection and continue
    │   ├── Not eligible → prevent selection/save and show approved reason(s)
    │   └── Cannot evaluate → do not falsely mark eligible; return approved validation state
    ├── Applicant may select Programme Option 2
    └── Repeat validation for Option 2
└── 3. Continue to Profile
    └── Only valid programme selections are persisted

Applicant Experience for an Ineligible Programme
Run the eligibility check when the applicant selects or saves a programme, before committing the preference.
If not eligible, keep the programme unselected and display a clear validation message.
Example: "You do not meet the admission criteria for this programme based on the academic information provided."
Where approved by the institution, show the unmet criterion, for example: "Required qualification: FSC Pre-Engineering."
Allow the applicant to return to Academic Information, correct/save the data, and retry.
Do not expose internal rule IDs, scoring logic, or sensitive administrative data.
Important Scope Decision
The current ADM-F000 source explicitly states that ADM-F000 publishes criteria and does not evaluate applicant eligibility. ADM-F002 requires validation against the published offering but does not define an eligibility engine, criterion vocabulary, rule syntax, or exact applicant-facing behavior for an ineligible programme. Therefore automatic eligibility evaluation is a proposed implementation enhancement and requires business approval.
Failure Handling
Programme Selection
├── Programme unavailable → reject → "Programme is not available for this intake."
├── Academic information incomplete → prevent evaluation → ask applicant to complete academic information
├── NOT_ELIGIBLE → reject → show approved eligibility reason(s)
├── Eligibility service unavailable → do not silently accept → return validation error/state
└── ELIGIBLE → persist programme preference
Submission Revalidation
Before final submission, revalidate the selected programme against the current published offering and approved eligibility rules using the latest saved academic information. This prevents stale programme selections from being submitted.
No Duplicate API Requirement
No new public eligibility endpoint is required. The existing F002 programme GET/PUT contract can return eligibility validation results during programme selection/save. An internal EligibilityService or integration adapter can perform the evaluation. This avoids creating a duplicate programme-selection or validation API.
